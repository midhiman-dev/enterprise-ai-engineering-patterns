# ADR-009: SQLite Persistence for DecisionTrace Audit Records

## Status
Accepted

## Date
2026-08-23

## Context
The Corrective RAG (CRAG) workflow builds an in-memory `DecisionTrace` domain entity to track execution steps (retrieval, document grading, query rewriting, web search, generation, hallucination checking, safe refusal). While this in-memory trace provides execution visibility during a single request, it does not provide durable auditability once request processing completes.

Future API, CLI, and UI components require access to historical workflow decision traces to allow developers and operators to analyze:
- Which graph nodes executed and in what sequence,
- Which routing paths were selected (e.g., straight local path vs. corrective web search path),
- Whether grounding verification triggered answer regeneration,
- Whether bounded retry limits resulted in safe refusal.

The primary architectural goal is to make workflow execution traces durable and queryable while remaining locally runnable with zero external infrastructure overhead.

## Decision
We implement a concrete SQLite repository adapter, `SQLiteDecisionTraceRepository`, behind the existing `DecisionTraceRepository` Domain port using Python's standard-library `sqlite3` module.

Key design points:
1. **Domain Boundary Isolation**: The `DecisionTraceRepository` Protocol in `domain/ports` remains the sole persistence contract. The Domain and Application layers have zero dependency on `sqlite3` or relational persistence details.
2. **Zero Third-Party ORM**: Standard-library `sqlite3` is used directly without SQLAlchemy or ORMs, ensuring learners can clearly follow the explicit mapping from Domain objects to relational SQL tables.
3. **Atomic Execution Persistence**: A completed `DecisionTrace` is persisted once at the workflow completion boundary via the `run_workflow` application use case, executing trace insertion and all ordered step insertions inside an atomic SQLite transaction (`with conn:`).
4. **Explicit Sequence Ordering**: Trace steps are stored with an explicit `sequence_number` column (0, 1, 2...) to guarantee deterministic step sequence reconstruction regardless of database physical row storage order.

## Alternatives Considered

### 1. In-Memory Repository
- *Pros*: Zero file I/O, simple implementation.
- *Cons*: Traces vanish when the application process terminates; fails the durability requirement.

### 2. JSON / JSONL File Storage
- *Pros*: Human-readable file format, simple append model.
- *Cons*: Weak queryability, lack of transactional atomicity across multi-file/index updates, risk of partial file corruption on process termination.

### 3. SQLite (Selected)
- *Pros*: Standard Python library (`sqlite3`), zero external infrastructure setup, ACID transactional guarantees, explicit schema, queryable with SQL, locally runnable.
- *Cons*: Single-file lock limits high concurrency; not intended for horizontally distributed microservice clusters.

### 4. PostgreSQL
- *Pros*: Production-grade concurrency, high write throughput, robust indexing, horizontal scaling support.
- *Cons*: Requires external database infrastructure and client SDKs (`psycopg`), introducing setup complexity for a local learning repository.

### 5. Distributed Tracing Frameworks (OpenTelemetry / Jaeger)
- *Pros*: Standardized distributed context propagation and RPC span timing.
- *Cons*: Designed for operational diagnostic latency and service call graphs, not domain-level workflow decision audit trails.

## Important Technical & Interview Distinctions

In production enterprise AI engineering, three distinct observability capabilities solve different problems:

| Concept | Primary Purpose | Examples |
| :--- | :--- | :--- |
| **DecisionTrace** | Semantic workflow decision & routing audit trail | Local retrieval vs. web search, relevance score outcomes, regeneration attempts, safe refusal |
| **Application Logs** | Operational diagnostic events & stack traces | Connection timeouts, memory allocation errors, unhandled exceptions |
| **Distributed Tracing** | Request propagation & service call timing | OpenTelemetry spans, HTTP request durations, RPC latency breakdown |

### Model Chain-of-Thought vs. AI Decision Trace
A critical security and governance distinction:
- **Model Chain-of-Thought (CoT)**: Hidden internal reasoning generated by LLMs (e.g., `<think>` tokens). CoT can contain unverified internal reasoning, prompt injection leaks, or non-deterministic reasoning steps.
- **Decision Trace**: Explicit, deterministic application workflow events and system routing outcomes recorded by application code. It stores system-verified execution decisions without relying on hidden model reasoning.

> **Interview Takeaway:**
> "I separate semantic AI decision traces from ordinary application logs and distributed telemetry. The DecisionTrace records why the workflow took a particular path—local retrieval, corrective search, regeneration, or refusal—while operational logs and distributed traces solve system diagnostic and latency problems. For local tutorial execution, I persist this through a Domain repository port using SQLite; production storage can evolve to PostgreSQL or an audit pipeline without altering the workflow's persistence contract."

## Transaction Semantics & Failure Policy
- A completed `DecisionTrace` persists atomically. If any step fails to insert, the entire transaction rolls back, preventing partially written audit traces.
- If database persistence fails, the repository raises an operational `RuntimeError`. Persistence failures are system failures and are never converted into `AnswerStatus.UNSUPPORTED` (which represents evidence/AI grounding outcomes).

## Current Trace Identity Limitation

### SQLite Internal Primary Key vs. Domain Identity
SQLite assigns an internal relational primary key (`decision_traces.id INTEGER PRIMARY KEY AUTOINCREMENT`) when a trace is persisted. That identifier is currently an Infrastructure implementation detail.

The Domain `DecisionTrace` entity and the `CorrectiveRAGApplication.run()` execution result do NOT expose a durable, externally addressable trace identifier. `DecisionTraceRepository.save()` returns `None`.

Therefore, helper queries such as `fetch_trace_steps_by_id(...)` exist purely as Infrastructure/local inspection capabilities. They do NOT constitute a stable public application or API contract. This decoupling is deliberate.

### Why Not Add UUID or Trace ID Now?
A public trace/execution identity must be introduced because an explicit application or API requirement demands it—not simply because a relational database table requires a primary key.

In production systems, an externally addressable execution/trace identity serves specific requirements:
- Returning an execution reference header in HTTP API responses,
- Querying a historical trace via an API endpoint (`GET /traces/{trace_id}`),
- Correlating workflow traces with application logs and distributed OpenTelemetry traces,
- Enabling distributed tracing, tenant isolation, or idempotency checks.

Database identity (auto-increment integer) and application identity (UUID, correlation ID) represent distinct concepts. Exposing an internal SQLite integer primary key into the Domain entity would accidentally leak persistence implementation details into the pure domain boundary.

### API Guardrail for Pass-14
Until an application-level trace execution identity is deliberately designed:
- Do **NOT** claim support for `GET /traces/{trace_id}` as a stable public API contract.
- Pass-14 may initially expose the decision trace inline within current request responses, or introduce an explicit execution correlation identity as a separate decision. Neither option is implemented in Pass-13B.

## Production Scaling Evolution (Design-Only)
For production deployment at enterprise scale:
- Replace `SQLiteDecisionTraceRepository` with a `PostgresDecisionTraceRepository` implementing the same `DecisionTraceRepository` Domain port.
- Introduce audit retention policies, partitioning by timestamp/tenant, correlation IDs (`trace_id` / `request_id`), and event streaming (e.g., Kafka / NATS) for async audit indexing.
